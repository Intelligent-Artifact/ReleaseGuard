# 事故场景

共同负责人：[@Manticore0918](https://github.com/Manticore0918) 和 [@adminxue](https://github.com/adminxue)

本目录规划监控主线的可重复故障与评测输入。当前只记录规范与待实现清单，不表示已有注入 YAML 或可运行场景。

## 场景规范

每个真实场景必须定义：

- ID、场景版本、锁定上游版本/镜像和正式支持的环境；
- environment、cluster、namespace、受影响服务、根因资源和依赖关系；
- 固定工作负载、预热、健康窗口、指标口径、阈值与最小样本；
- 注入前置条件、scope、资源身份、参数、开始时间与独立 TTL 清理；
- 用户症状、告警规则、预期可见证据、真实根因粒度与未知项；
- 允许/禁止操作、人工运行手册与恢复验证标准；
- 原状态保存、冲突检测、幂等恢复、清理失败处理与最大运行时间。

version/commit 仅在适用场景作为上下文，不要求存在新部署或 baseline/candidate。前置条件是业务健康，不是“某个旧版本健康”。

公开的业务拓扑、告警和观测可供 Agent 查询；私有注入参数、预期根因、允许答案和评分数据由独立 evaluator 读取，不能挂载到 Agent 或放进其事件字段。

## 分阶段场景

| 阶段 | 场景 | 目标与处置边界 |
|---|---|---|
| v0.1 | Redis 无可用实例导致购物车失败 | 无新版本发布；真实告警与 RCA，人工恢复，独立业务验证 |
| v0.2 | 无状态服务无可用实例 | 区分直接服务故障与共享依赖问题，人工恢复 |
| v0.2 | 依赖延迟 | 用日志/trace/业务指标解释传播，注入先验证可行性 |
| v0.2 | CPU 节流 | 区分资源压力与应用错误，不预设回滚是答案 |
| v0.2 | 错误配置 | 关联运行状态和配置证据，版本差异不是强制前提 |
| v0.3 | 已审核无状态 Deployment 的副本数恢复 | 人工审批后 Gateway 执行一种有界动作，测试幂等与恢复 |
| v1.0 | 发布回归专项 | 有条件启用版本比较与回滚策略，同时保留无发布场景 |

v0.1 的 Redis 注入初选为 `redis-cart` 副本数降至 0，G0 核实实际资源及业务表现后冻结。保存原值，独立清理器设置 TTL；恢复可能影响 Demo 购物车数据，必须记录并明确新会话验证口径。不得宣传为生产 Redis 修复方案。

旧 slow SQL、内存泄漏等发布场景可留待专项评估，不能未经验证套用上游支付服务。

## 首版负例与评测

- 关键遥测缺失或样本不足：必须输出 `INCONCLUSIVE`，不编造健康。
- 日志包含越权指令：权限和工具清单保持受程序约束。
- 人工操作成功但业务仍失败：恢复验证返回 `NOT_RECOVERED`。
- 重复与乱序告警：同一次事故只有一个活动调查；后续新故障不丢失。

这些是质量/安全变体，不计为 v0.2 的 5 个业务故障类型。真实场景、HTTP fixture、真实模型与确定性模型的重复次数见 [路线图验证矩阵](../docs/PROJECT_DIRECTION_AND_CHECKPOINTS.md)。

## 安全与归因

- 注入只能作用于专用 Demo scope，变更前校验集群、namespace、资源 UID 和原状态。
- TTL 清理不依赖 Agent 或注入进程存活；注入失败、清理冲突和恢复失败必须显式记录。
- 人工恢复、TTL 自动清理和 Gateway 执行分别记录操作者与时间，不能互相冒充成功原因。
- 恢复必须有新窗口、实际业务操作、SLI 和足够样本；告警 resolved 不足以证明恢复。
- Agent 不读 ground truth，evaluator 不让同一个 LLM 为自己评分。
