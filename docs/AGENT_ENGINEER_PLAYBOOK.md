## 1. 交付目标与当前状态

你的首版成果是：真实监控告警自动触发一次有预算的调查，Agent 经 HTTP Gateway 关联版本锁定的 Online Boutique 运行环境中的业务与平台证据，输出可核查的根因判断、人工建议和恢复报告。ReleaseGuard 是独立主仓库；Online Boutique 无论直接使用上游制品还是通过独立 fork 构建，都只是被调查的运行依赖。

作品集先证明“能调查一个真实事故、能说明不知道什么、能验证恢复”。技术深度随后用对照实验、故障变体、重启恢复和受控执行补足。版本对比是后续专项，调查不要求 baseline/candidate 或 Git diff。

已有 `agent/src/releaseguard/` 的 fixture smoke、LangGraph harness、模型/数据源适配边界和报告代码可以复用。当前 harness 仍依赖部署与版本比较证据，默认使用确定性替身；真实 HTTP client、监控事件、真实 LLM 与无发布调查尚待实现。本手册中的新字段和状态是设计目标，不能视为已有接口。

## 2. 职责边界

| 事项 | Agent 负责人 | 平台负责人 |
|---|---|---|
| 告警产生与入口 | 消费规范化事件 | SLI/SLO、Alertmanager、认证入口、事件保存与去重 |
| 调查生命周期 | 创建调查、状态推进、预算、证据和报告 | 提供稳定 incident ID、事件时间线与查询数据 |
| 数据访问 | 受限 HTTP 工具、参数和结果校验 | 查询模板、后端凭据、来源与错误语义 |
| 上游运行身份 | 在调查、报告和评测中引用已验证的锁定标识，不从模型猜测版本 | 维护上游锁定清单，验证实际清单、镜像及可选 fork base |
| 根因分析 | 区分症状/根因、替代假设、未知项 | 真实依赖关系、资源状态与可追溯遥测 |
| 首版恢复 | 生成人工建议，读取独立验证结果 | 运行手册、人工操作记录、真实恢复验证 |
| v0.3 执行 | 提案、策略预检、状态跟踪 | 策略强制、审批签发/校验、执行、幂等与审计 |
| 评测 | 外部 scorer、结果分析、模型对照 | 注入事实、环境重建、清理及恢复 ground truth |

Agent 不直连 Kubernetes、Prometheus、Loki 或 Tempo，不持有基础设施凭据。Agent 不读取注入参数和答案目录，不签发自己的审批令牌，不将自然语言转换为任意 shell。

## 3. 首版技术范围

沿用当前 Python / LangGraph 基础，按功能逐步扩展 `agent/src/releaseguard/`；不要为了计划先重建目录或引入通用 Agent Runtime。

- 一个 Agent 进程，消费 Gateway 的规范化事件；一个真实模型适配器与一个确定性替身。
- Gateway 通过受限分页返回待调查事件；Agent 按 incident ID 建立唯一调查并持久记录接收状态。
- 工具仅包含事件读取、指标、日志、依赖/资源状态与恢复查询。
- 显式预算、超时、取消、返回大小与查询范围限制。
- JSON/Markdown 报告和机器可读工具轨迹；可直接用于展示，不先制作聊天前端。
- 首版保存事件、调查概要和状态转换；进程故障后显示中断并支持显式重新运行，自动 checkpoint 续跑在 v0.2 验收。

事件自动触发是首版必要条件。手工 CLI 可以用于调试、fixture 重放和现场排错，不能代替真实告警触发链路。

## 4. 调查模型与迁移

### 4.1 Investigation

监控调查的核心上下文应包含：

- `investigation_id`、`incident_id`、事件 `fingerprint`；
- `environment`、`cluster`、`namespace`、初始 `service`；
- 告警来源、症状、严重程度、事件开始/接收时间；
- 明确的查询时间窗、允许访问的服务集合或依赖边界；
- 当前状态、预算、模型/规则版本与运行 ID。
- 本次 live 运行引用的上游锁定清单版本，以及平台已验证的 release、commit、镜像 digest 集合或其稳定引用。

`baseline_version`、`candidate_version`、`deployment_id` 不再是创建调查的必填项。查询到版本时保留；没有版本资料时使用明确的缺失语义。受影响服务和根因资源分别记录，例如 `cartservice` 与 `redis-cart`。

上游 release/commit/digest 属于运行可追溯元数据，不等同于发布回归证据，也不能因为存在版本号就推断事故由变更引起。Agent 不读取 Online Boutique 源码仓库、fork 分支或补丁作为隐藏答案；如后续发布专项需要 Git 证据，仍须经受限 Gateway 和独立契约提供。

### 4.2 Evidence

每条证据至少记录 ID、类型、来源系统、scope、资源/服务、观测区间、采集时间、查询引用、摘要、原始来源引用，以及完整性/新鲜度/单位/样本量。

- 告警描述只用于确定症状和初始范围，不能单独证明根因。
- 同一指标生成的告警和查询结果不能当作两个独立来源。
- 来自不同服务的证据可以关联，但必须存在可核查的依赖路径，且处于相容时间窗及授权范围。
- scope 由入口与程序决定，模型不能用日志中的服务名自行跨 namespace 查询。
- 对当前 SLO、历史健康窗口和健康实例分别标注参照类型；历史窗口需检查工作负载、指标单位和样本可比性。
- 无数据、过期、不完整和不可比要结构化返回，不能被解释成 0 错误或正常。

### 4.3 Finding 与建议

建议将诊断、响应和恢复分开，拟定枚举见契约迁移计划：

- 诊断：`CONFIRMED`、`INCONCLUSIVE`、`NO_INCIDENT`。
- 响应：`OBSERVE`、`MANUAL_REQUIRED`；`PROPOSE_ACTION` 在 v0.3 启用。
- 恢复：`NOT_REQUESTED`、`VERIFYING`、`RECOVERED`、`NOT_RECOVERED`、`INCONCLUSIVE`。

`CONFIRMED` 必须有至少两类独立来源支撑具体断言，给出替代假设、反证或未排除项。置信度是辅助表达，不是审批依据。若只确认 Redis 不可用而无法确认使其不可用的操作者或配置来源，应明确根因粒度，不能编造事故起因。

`NO_INCIDENT` 需要有效的健康证据，只适用于调查窗口内未验证到异常；故障已发生且后来恢复时仍保留该故障结论。`INCONCLUSIVE` 不能因报告已生成而被标记为恢复。

旧 `PROMOTE/HOLD/ROLLBACK` 语义保留在旧发布路径，不能让普通运行故障继续被迫选择发布决策。

## 5. 告警消费与调查状态

Gateway 负责接收 Alertmanager 通知、拆分批量告警、保存事件和精确去重。Agent 负责以 `incident_id` 保证调查创建唯一性；可重复消费事件，不能重复开始相同活动调查。

同一 fingerprint 的新一次故障具有新的事件起始时间和事故 ID；不能永远合并到旧事故。resolved 事件、乱序通知和重复 firing 的具体规则由 G1 fixture 固定。首版只做同一告警事件的精确去重，跨服务事故关联在 v0.2。

首版拟采用的状态路径：

```text
RECEIVED → COLLECTING → ANALYZING → REPORTED
                                      → AWAITING_MANUAL → VERIFYING
                                      → RESOLVED | RECOVERY_FAILED

任意执行阶段 → FAILED | INTERRUPTED
```

状态描述流程进度，Finding 描述诊断结果，两者不能混用。证据不足可以结束本次调查为 `REPORTED` 并输出 `INCONCLUSIVE`，不要求假造操作。人工标记操作完成后才启动恢复验证；告警 resolved 只是一条新证据。

每次转换记录前后状态、触发者、时间、证据引用、原因、模型/工具版本和错误。首版重启时把未完成运行显示为中断；v0.2 增加持久化 checkpoint 与安全续跑，避免把一次新运行伪装成从未中断。

## 6. 工具与调用边界

以下是拟实现的逻辑工具；最终路径与 schema 以双方冻结的 OpenAPI 为准。

| 工具能力 | 首版输入重点 | 返回重点 |
|---|---|---|
| 获取事件 / 事故 | incident ID、分页游标、scope | 规范化告警、事件状态、时间线 |
| 查询指标 | service/resource、模板 ID、起止时间、可选参照 | 数值、单位、样本量、阈值与来源 |
| 查询日志 | 已授权 service、窗口、固定过滤参数 | 聚合、代表性日志、截断标记、原始引用 |
| 查询依赖与资源状态 | service/resource、namespace、窗口 | 依赖路径、ready/desired 状态、事件与来源 |
| 查询恢复结果 | incident ID、恢复记录 ID、验证窗口 | 业务检查、样本、SLI、结果和来源 |
| 查询 traces | v0.2：service、窗口、trace ID | span、错误与路径，缺失/采样说明 |
| 查询部署 / 变更 | v1.0 专项，可提前只读复用 | 版本、时间、资源变化与 Git 来源 |

模型不提交原始 PromQL、LogQL、资源 patch 或命令。程序校验时间范围、服务集合、参数类型、查询模板、最大结果和调用预算；Gateway 再次校验。工具故障区分超时、无数据、权限拒绝和后端不可用。

不要把现有 harness 的 4 次模型 / 3 次工具预算无条件沿用为多源调查最终预算。在 G2 根据样例设一个固定上限并记录依据，测试预算耗尽后明确退出，不能无限放宽直到得到理想答案。

## 7. 首个真实调查流程

1. 从真实告警读取购物车业务失败症状、时间和 scope，保存原始事件引用。
2. 查询异常窗口的业务成功率、延迟和请求量，确认确有用户影响。
3. 查询 `cartservice` 的依赖错误日志；日志中没有的异常类型不得补写。
4. 沿已验证依赖关系查询 `redis-cart` 的副本、就绪和相关资源状态。
5. 区分 Redis 无可用实例、购物车自身故障、网络问题和采集失败等假设；只排除有反证的项。
6. 输出受影响服务、可证实的根因粒度、引用、未知项和受限人工运行手册建议。
7. 人工恢复后，经 Gateway 查询新窗口，独立展示购物业务、错误率、延迟和样本量是否满足标准。
8. 写入完整报告，保留人工恢复、TTL 清理或未恢复等实际结果。

G0 必须验证实际依赖和失败现象，并由双方核对 Agent 报告所引用的上游锁定标识与平台实际部署一致。身份不一致的 live 运行应在调查前置检查中失败或明确标为不可验收，不能悄悄继续并计入结果。禁止从场景名称、固定字段或注入标记直接映射到答案；公开静态拓扑是可用上下文，私有注入参数不是。

## 8. 真实模型、替身与演示方式

| 运行方式 | 数据源 | 模型 | 用途 |
|---|---|---|---|
| fixture 回归 | HTTP fixture Gateway | 确定性替身 | 无外部模型网络的 CI、负例与契约检查 |
| live 回归 | Online Boutique 真实遥测 Gateway | 确定性替身 | 验证平台链路、重复性和恢复流程 |
| live LLM | 同一真实 Gateway | 真实 tool-calling 模型 | 作品集现场调查和后续质量评测 |

三种方式共用调查引擎、schema、证据校验和报告；替身用于可重复验证，不能被宣传为 LLM 质量。报告必须标明数据源、模型方式和上游锁定清单引用；若运行来自独立 fork，还要标明 fork URL、base commit 与补丁版本，但不把上游代码计入 Agent 原创贡献。

首版至少保留一次真实 LLM 的正常调查和一次恶意日志安全样例；单次成功只证明路径可运行。模型不可用时保留失败信息，现场可切换明确标注的回放，但不能把回放记录伪装成现场推理。

## 9. 人工恢复与后续动作

v0.1/v0.2 只生成人工建议，写工具不注册，Gateway 的监控运行身份也无执行权限。建议必须引用已审核且有版本的运行手册，指出范围与前置条件，不能输出任意资源修改指令作为执行入口。

人工操作由独立操作者记录 ID、身份、目标、时间和结果，作为操作声明写入报告。Agent 不能伪造操作者，也不能因为人点击“已恢复”就宣布 `RECOVERED`。

v0.3 才引入 `PROPOSE_ACTION`，先支持已审核 Demo 无状态 Deployment 的副本数恢复：

- 提案绑定调查、证据、目标 UID、预期当前状态、目标副本数、策略版本和过期时间。
- Agent 做策略预检，Gateway 重新强制裁决；所有写动作均需人工批准。
- 审批凭据由 Gateway 管理，绑定 payload hash，不由 LLM 生成。
- 审批状态与执行、恢复状态分离；拒绝/过期不等于故障已解决。
- 提交超时后按稳定 action ID/幂等键查状态，不换 key 盲目重试。
- 执行成功但恢复失败时转人工，不串行尝试其他修复动作。

数据库操作、PVC 删除、任意网络/RBAC 修改、跨 namespace 写入与自由 shell 不进入开放动作集合。

## 10. 测试与外部评测

### 10.1 首版必须验证

- 同一告警重复投递只创建一个活动调查，resolved 与后续新故障语义正确。
- live 前置检查能发现锁定清单与实际部署镜像或 fork base 不一致，并阻止该运行进入正式评测。
- 没有部署、版本或 Git 证据时仍能完成 Redis 场景。
- 依赖证据可以跨服务关联；无依赖依据的跨 scope 引用被拒绝。
- 有效 ID 不等于有效因果证据，报告断言必须由引用内容支持。
- 无数据、低样本、过期、冲突、未知工具、超时和预算耗尽均明确退出。
- 恶意日志不能改变工具权限或目标；真实模型也有程序外部约束。
- 人工操作成功、告警 resolved 或 TTL 清理均不能跳过真实恢复检查。
- 保留既有发布 fixture 测试，确保迁移不静默破坏旧行为。

完整重复次数与验收方式以共同路线图的“首版验证矩阵”为准。

### 10.2 v0.2 技术实验

- 规则基线与 LLM：固定同一组证据可见性，比较正确率、拒答、调用数和成本。
- 单源与多源：移除日志、平台状态或 trace，观察根因粒度和误判变化。
- 未见变体：隐藏服务名变体、故障强度或时间参数；训练/调试样例与评测样例分离。
- 持久化：调查中途退出、重复消费、工具响应迟到、检查点损坏及恢复。
- 告警关联：重复风暴、同症状不同根因、同依赖多服务失败，报告误合并与漏合并。

Ground truth 由独立 evaluator 读取，不能挂载到 Agent，也不能用同一个 LLM 自评替代外部事实评分。记录代码 commit、模型标识、prompt、schema、场景版本、上游 digest、流量、全部运行结果与失败分母。

## 13. 展示与面试材料

首版由你讲解：一个告警为何触发调查、工具为何这样选择、证据如何支持根因、还有什么不知道，以及人工恢复后如何判断结果。

保留一份“不确定”报告，说明系统为何停止；展示两类来源，避免只读一段模型回答。报告中标注 Google 提供业务应用及其锁定版本；若使用独立 fork，区分上游、最小业务补丁与 ReleaseGuard 原创成果。你负责调查引擎、校验、模型适配和评测。
