## 1. 交付目标与当前状态

你的首版成果是：一个可重建的 Online Boutique 环境，具有真实购物流量、业务 SLI、告警、证据查询、故障注入和独立恢复验证，能够支撑 Agent 完成一次实际调查。

作品集首先展示完整运行链路和你的独立贡献；后续通过遥测质量、故障恢复、安全执行和 GitOps 实验增加技术深度。电商业务由上游提供，你负责运行与可靠性工程。

仓库当前已有自研应用原型和 CP0 HTTP Mock Gateway。Online Boutique、真实监控、监控事件入口、恢复验证和安全执行均待实现；本手册中的新目录、接口与命令交付要求不代表它们已经存在。

## 2. 职责与协作边界

你负责上游版本锁定、Kubernetes 部署、资源预算、业务流量、Prometheus/Alertmanager、日志采集、Gateway、故障 TTL/清理、人工运行手册与恢复验证；后续负责 traces、Executor、审批、审计和 GitOps。

Agent 负责人负责事件消费、调查状态、工具 client、证据校验、模型推理、报告和外部 scorer。双方共同确定场景答案、契约、恢复阈值、E2E 与验收材料。

你的交付不能止于“应用部署成功”；必须证明业务失败能被监测、告警能触发调查、证据可被查询且恢复可验证。也不需要为 Agent 写 prompt 或重新开发订单、支付、优惠业务。

## 3. Online Boutique 集成策略

### 3.1 上游与维护方式

采用 [GoogleCloudPlatform/microservices-demo](https://github.com/GoogleCloudPlatform/microservices-demo) 作为被监控应用。上游提供购物流程、服务依赖和 Locust 流量生成器；本项目的 README、演示与制品说明要明确其来源。

- G0 选择并验证固定 release，记录 commit、镜像 digest、清单来源和许可证；不预先宣称某个未测试版本可用。
- 默认使用上游发布镜像与清单，通过本地 Kustomize overlay 保存命名空间、资源、采集与演示差异。
- 不复制整份业务源码进本仓库；按需保存可复现下载/校验流程。必须补埋点时保留最小补丁、基准 commit、构建方法和补丁理由。
- 保留上游许可证和必要 NOTICE，第三方源文件及许可证原文不改写；集成说明和自行新增注释使用中文。
- 上游升级以独立任务完成，重跑健康、注入、证据和恢复检查；不能在录屏前临时切换浮动版本。

上游官方开发指南支持 Kind、Minikube 与 Docker Desktop Kubernetes。本项目以 **本地 Kind** 作为首选验收环境，G0 记录操作系统、容器运行时、CPU 架构和网络条件。无需先部署 GKE；镜像拉取和多服务开销需要实际验证。[官方开发指南](https://github.com/GoogleCloudPlatform/microservices-demo/blob/main/docs/development-guide.md)

### 3.2 部署范围与诊断范围

优先部署上游必要依赖，避免为了“只部署三个服务”花时间修改业务调用。**部署完整依赖不等于承诺诊断所有服务**：首版正式覆盖购物车到 Redis 的链路，其他服务仅维持购物流程。

原有 `platform/apps/` 三个自研服务保留为历史原型，不再扩展业务功能。原 slow SQL 场景不能直接假设适用于上游 `paymentservice`，新故障必须先验证真实载体和信号。

### 3.3 建议新增的资产

以下均为待实现路径，目录按实际功能逐步创建：

| 建议位置 | 内容 |
|---|---|
| `platform/online-boutique/` | 上游锁定清单、来源说明、下载校验与 Kustomize overlay |
| `platform/observability/` | Prometheus 规则、Alertmanager、Loki、Grafana 看板；后续 OTel/Tempo |
| `platform/workload/` | Locust 配置、合成业务检查、预热与采样参数 |
| `platform/gateway/` | 保留 CP0 Mock，增加监控事件、真实只读适配器和验证器 |
| `platform/faults/` | 独立注入器、TTL 清理器、恢复前置检查 |
| `platform/runbooks/` | 启停、恢复、故障排错、清理与环境重建 |

不要仅为目录完整而创建空框架，也不要先引入 Helm、Argo、Terraform 和 Service Mesh 的完整组合。

## 4. v0.1 最小平台

| 组件 | 首版责任 | 可推迟内容 |
|---|---|---|
| Kind + 上游清单/overlay | 单个 Demo 环境、固定版本、明确资源限制 | 多集群、云环境、复杂 Helm |
| 上游 Locust + 最小合成检查 | 稳定购物流量与可量化业务健康 | 大规模压测平台、自建第二套业务流量框架 |
| Prometheus + Alertmanager | SLI、阈值、持续时间、告警投递 | 多窗口 burn-rate、复杂告警拓扑 |
| Loki + 日志采集器 | 目标链路日志查询与来源引用 | 全部语言统一日志库 |
| Kubernetes Reader | 目标依赖、ready/desired、资源事件 | 集群级任意查询 |
| Grafana | 业务健康与事故时间线两个最小视图 | 自研前端、大量仪表盘 |
| Ops Gateway | 事件入口、只读取证、人工记录与恢复查询 | 自动写动作、审批令牌和 Executor |

CPU、内存、磁盘与启动时长在 G0 实测。官方应用资源建议不能直接当作“应用 + 监控 + Agent”的总需求；记录稳态和故障期间峰值。资源不足时先缩减非关键采集和负载，保留必要业务依赖与真实告警，不切回 Mock 后声称达成 live 验收。

## 5. 遥测覆盖与告警

### 5.1 先验证实际上游能力

官方 Google Cloud Operations 组件默认关闭，组件说明还标注目前仅支持 trace；不能把上游存在 OpenTelemetry 配置等同于完整指标/日志/链路已经可用。本项目在 G0 必须对选定版本重新验证。[官方组件说明](https://github.com/GoogleCloudPlatform/microservices-demo/blob/main/kustomize/components/google-cloud-operations/README.md)

建立覆盖矩阵，记录每个首版信号的实际来源、采样方法、单位、标签、窗口、缺失表现与例子：

| 首版需要的信号 | 来源选择与验证重点 |
|---|---|
| 购物车业务成功/失败 | 优先可用埋点；缺失时用受控合成操作导出，不用首页 HTTP 200 代替购物车成功 |
| 请求量与延迟 | 确认统计对象是请求还是探测，分母与单位明确，禁止把探测样本称为全量用户请求 |
| cartservice 依赖错误 | 真实 stdout 日志采集，保留时间、资源和原始引用 |
| Redis 可用状态 | Kubernetes desired/ready、副本或端点状态；故障为何发生需额外证据 |
| 依赖关系 | 固定上游配置或已观察的调用关系，说明是静态拓扑还是实际 trace |

首版允许日志采集层做字段映射，不强迫所有上游服务提供自研原型的 `/metrics`、`/version` 或相同日志 schema。traces 在 v0.2 正式接入；首版报告不能引用尚不存在的 span。

### 5.2 指标与规则

- Prometheus 持续采集，记录规则生成业务 SLI；Agent 不负责轮询原始指标做监控。
- G0 采样正常窗口，冻结错误率、延迟、告警持续时间、最小样本和恢复窗口；阈值写入场景配置及报告，不让模型临时选择。
- 首版主告警围绕购物车业务失败，Redis 状态用于诊断佐证。健康探针、Pod Ready 和业务成功分别记录。
- 按 environment、cluster、namespace、service、固定业务操作等低基数维度聚合。版本可选，trace ID、用户 ID 和完整 URL 不作为高基数指标标签。
- 不把流量升高直接判为故障；无数据和采集失败触发不同状态，不能当作健康。
- 恢复窗口从实际恢复操作后开始，包含足够新样本，不重复使用故障前健康窗口。

### 5.3 日志与后续 traces

Loki 采集目标链路日志，保留 observed/collected 时间、资源标签、severity、message 和来源引用。Gateway 使用固定过滤模板返回聚合与代表性事件，限制窗口、条数和字节数，并报告截断。

日志、annotation 和错误文本均不可信，禁止将其作为指令。脱敏 token、个人信息及请求中的敏感字段；trace ID 放结构化字段，不用作 Loki 索引标签。

v0.2 接入目标链路 OTel/Tempo：核查上下文传播、资源属性、采样与丢失 span，测量 Collector 故障对业务和调查的影响。未观察到 span 不等于调用未发生。

## 6. 告警入口与事故事件

Gateway 接收 Alertmanager 通知，验证来源和 payload 大小，拆分批量告警并保存后确认；临时失败应允许上游重试。它输出稳定 incident ID，Agent 轮询事件并自行创建调查。

G1 最小规则：

- 事件 scope 包含 environment、cluster、namespace、service；告警来源和 labels 经过校验与映射。
- 同一次告警的来源、scope、fingerprint 与 startsAt 共同确定事故身份，重复投递追加接收记录而不新建事故。
- resolved 更新事件状态但不证明系统已恢复；乱序 firing 不重开已结束的同一次事件。
- 同一 fingerprint 后来发生的新故障有新 startsAt 和新 incident ID。
- Gateway 保存事件与投递状态；Agent 以 incident ID 去重。重试和分页不能依赖模型记忆。
- 首版仅保证精确去重，跨服务告警聚合、风暴控制和可靠续跑在 v0.2。

事件内容不包含场景答案、故障注入名称或私有评分字段。人工触发测试事件应标为 replay，不能代替真实 Alertmanager 的 live 验收。

## 7. Ops Gateway 与契约

当前 `/api/v1` 仍是发布回归草案，保留原行为与 fixture。监控能力拟用 `/api/v2` 独立定义，具体契约任务见 [迁移计划](../contracts/MONITORING_CONTRACT_PLAN.md)。不要在现有 metrics compare 中塞一个虚假的 candidate 来兼容新场景。

首版最少能力：事件列表/详情、模板化指标、日志、依赖与资源状态、人工干预记录、恢复验证查询。每个响应包含请求 ID、生成时间、scope、来源、质量警告与稳定错误码。

- 服务、namespace、查询模板和时间窗有 allowlist 与上限。
- 查询请求不接受自由 PromQL、LogQL、shell 或 Kubernetes patch。
- 原始数据引用不能是 Agent 可任意读取的文件路径或无约束 URL；通过授权查询才能取回。
- HTTP fixture 与 live 适配器使用同一 schema，报告标明数据来源。
- 当前 CP0 rollback Mock 不连接真实集群，不能被监控运行身份用于写入；真实 v0.1 Gateway 仅启用只读适配器。
- 当前没有的部署、版本、Git 信息显式缺失，不阻塞普通事故调查。

v0.1 可以使用本地持久事件存储及单 Gateway 进程；不承诺高可用。记录进程中断和不可用，v0.2 再验证可靠恢复与积压消费。

## 8. 首个故障与人工恢复

### 8.1 Redis 无可用实例

初始方案：专用 Demo namespace 的 `redis-cart` Deployment 副本数降到 0。G0 先确认选定上游版本的资源名称、控制器类型、业务失败表现和日志证据，再固定场景。

注入器必须：

1. 确认集群身份、namespace 和资源 UID 属于 Demo allowlist。
2. 验证购物流程健康、流量足够，保存原副本数与清理所需状态。
3. 在变更前注册独立 TTL 清理，清理器不能依赖 Agent 或注入进程存活。
4. 执行有界注入并独立确认故障真实发生；记录时间供 evaluator 使用。
5. 支持恢复原值的幂等清理、冲突检测和人工接管；不能静默覆盖别人的新状态。

这一操作没有发布新应用版本，但改变了运行状态。Agent 可读取正常 Kubernetes 状态证据，不能访问注入指令或答案文件。

### 8.2 人工运行手册

首版由操作者确认调查建议后，根据运行手册恢复保存的原副本数。运行手册必须包括 scope 检查、资源身份、前置状态、操作步骤、验证、失败处理和清理；保存操作者、目标、时间及结果引用。

场景仅用于可丢弃 Demo 数据。G0 要核实 Redis 重建对购物车状态的影响，记录数据是否丢失；恢复验证使用明确的新会话或重建测试数据，不宣称历史购物车已恢复，也不把此操作推广为生产有状态服务修复。

人工干预记录由独立操作者身份或平台运行工具提交，Agent 只读；记录的“成功”是操作声明，最终恢复结论仍来自验证器。

### 8.3 TTL 与评测归因

TTL 到期清理优先保证环境回收。如果清理器先恢复服务，报告记为 TTL 清理，不记为 Agent 或人工建议的修复成功。评分记录实际注入、检测、人工操作、TTL 和验证时间，操作来源不能混淆。

若注入失败、清理冲突或清理失败，该运行应标记为环境失败并保留记录，不进入诊断成功样本。

## 9. 独立恢复验证

验证器通过新的观测窗口判断结果，不能只看副本恢复、操作退出码或告警 resolved。

首版必需检查：

- 目标依赖达到约定 ready/desired 状态。
- 实际购物车合成操作连续通过，必要的测试数据已正确初始化。
- 错误率、延迟回到冻结阈值内，统计口径与故障前一致。
- 新窗口有足够样本，数据采集没有过期或中断。
- 在完整观察窗口内持续满足条件，不能只取一个好样本。

返回 `RECOVERED`、`NOT_RECOVERED` 或 `INCONCLUSIVE`，附每项检查、实际值、阈值、窗口、样本量和来源。业务仍异常时 `NOT_RECOVERED`；数据不够判断时 `INCONCLUSIVE`。v0.3 执行状态与恢复状态仍分别记录。

恢复失败由人继续处理，禁止无上限地重复重启或扩容。必须保留“人工操作/命令成功但业务仍失败”的负例，证明验证器独立。

## 10. 安全边界与后续执行

### 10.1 首版身份

| 身份 | 最小能力 |
|---|---|
| Agent | 只读 Gateway 的授权事件、证据与验证结果，无集群/遥测凭据 |
| Gateway Reader | 目标 namespace 的必要资源状态、受限遥测查询 |
| 操作者 | 独立执行已审核运行手册、记录人工操作 |
| Fault Injector / Cleaner | 专用 Demo 的限定注入与清理，不能进入 Agent 身份 |
| Evaluator | 读取 ground truth 与报告，独立评分 |

凭据不入 Git 或日志；限制入口访问和请求速率。Agent 与执行/注入工具隔离，无法读取其凭据或答案。使用 NetworkPolicy 时必须验证实际 CNI 支持并做连通性负测，不能仅靠 YAML 文件声称隔离已生效。

### 10.2 v0.3 唯一首发写动作

在已审核 **无状态 Deployment** 场景提供副本数恢复，绑定目标 UID、当前预期副本数、明确目标数及数值上限。不要直接把首版有状态 Redis 场景作为自动动作对象。

Gateway Executor 必须验证：allowlist、操作者权限、提案有效期、payload hash、人工批准、资源身份与前置状态、目标并发锁和幂等键。所有写动作需要批准；LLM 的风险自评不能授予权限。

审批、执行、恢复分别建模。审批可拒绝或过期；执行通过异步 action ID 查询；恢复通过新遥测检查。同 key 同 payload 返回同 action，不重复副作用；同 key 不同 payload 返回冲突。

持久化动作日志，测试平台已生效但响应丢失、执行器重启、状态竞争和存储不可用。不要在消费一次性审批后让同一次授权动作的幂等查询/重试失效；它也不能被拿去创建新动作。

禁止任意 patch、shell、删除 PVC、数据库变更、网络/RBAC 修改及跨 namespace 写入。读写 ServiceAccount 与运行路径分离，Executor 不拥有 cluster-admin。

## 11. 分阶段实施清单

| 阶段 | 平台任务 | 退出证据 |
|---|---|---|
| G0 | 锁定上游、最小 Kind、业务/Redis 故障验证、TTL 与资源检查 | 覆盖矩阵、锁定清单、原始采样和恢复记录 |
| G1 | Prometheus/Alertmanager/Loki、Gateway 事件与查询、最小看板 | 真告警到唯一调查的 HTTP 链路 |
| G2 | 真实证据适配、scope/时间窗/错误语义，与 Agent 复验 | 多源 RCA 所需证据可追溯，缺失不伪装 |
| G3 | 人工运行手册、独立验证、E2E、录屏和环境重建 | 首版验证矩阵、业务恢复曲线与双方签收 |
| v0.2 | 目标 traces、5 故障、告警风暴和遥测中断实验 | 质量/开销/失败结果及可重复实验 |
| v0.3 | 单写动作、审批、持久化幂等、并发、审计 | 安全负测、崩溃恢复、假恢复拒绝 |
| v1.0 | GitOps、CI/CD、漂移与发布专项 | 状态竞争实验、可追溯制品、环境重建 |

v0.2 新增的服务无可用实例、依赖延迟、CPU 节流和配置故障都要先确认注入方法与可观测性；不要为了凑数量把遥测缺失当作第五种业务根因。

## 12. CI 与验证

首版 CI 聚焦：旧契约兼容、新契约 fixture、Gateway 参数/事件去重、真实数据适配与恢复判定。Kubernetes 清单渲染、配置检查和针对改动的镜像构建随实际资产加入。

live E2E 在隔离的受支持环境执行，外部贡献 PR 不接触部署凭据。真实模型使用独立受控运行，普通 CI 使用确定性替身。每次发布保存上游 digest、规则、场景、流量、代码 commit 与实际命令输出。

首版验收至少包括：从干净 clone 启动；真实告警自动触发；重复投递去重；无数据显式失败；Agent 无写权限；TTL 在注入器退出后仍清理；人工恢复后业务验证；操作成功但未恢复；连续 3 次注入/恢复/清理。

v0.2 补充 Gateway/Agent 重启、积压消费、日志/trace 延迟和告警风暴。v0.3 补充审批重放、不同 payload 冲突、并发目标、状态变化、执行响应丢失及存储故障。

## 13. 作品集材料与现场演示

首版由你展示：应用归属与拓扑、真实业务健康、故障注入的边界、告警到 Gateway、可查询证据、人工恢复、验证窗口和清理结果。控制在共同 5–8 分钟演示中的平台部分，不逐页展示全部 YAML。

必须交付：

- 两个最小 Grafana 视图的版本化配置和恢复前后截图。
- 从干净环境启动、运行 live demo、fixture 验证、停止与清理的确切命令。
- 资源需求、镜像获取和模型凭据前置条件，区分首次联网安装与后续运行。
- 一次真实告警、一次假恢复拒绝、一次清理记录。
- 上游归属说明、你的功能 PR、对 Agent 的 review 和联合 E2E 记录。

v0.1 不用完整 tracing、Argo 或云部署阻塞发布；技术附录在对应版本加入一次可复现实验和前后对比，避免只罗列工具名称。

## 14. 面试深挖与运行手册

| 技术问题 | 对应实验或材料 |
|---|---|
| 告警为什么可信？ | 合成检查与用户业务的差异、阈值基线、低流量和缺数测试 |
| 依赖故障如何传播？ | Redis 场景时间线，v0.2 trace 与多服务证据 |
| 为什么不直接给 Agent kubectl？ | Reader/Executor 权限、scope 负测、审计记录 |
| 如何证明没有重复执行？ | v0.3 幂等存储、并发锁、响应丢失与重启实验 |
| GitOps 会不会马上撤销操作？ | v1.0 临时故障、紧急恢复与期望状态竞争实验 |
| 平台成本与可靠性如何权衡？ | CPU/内存、采样率、查询预算和采集失败的测量 |

首版运行手册至少覆盖：环境启停与重建、Redis 故障与人工恢复、告警未到达、Prometheus 无数据、日志标签/延迟错误、恢复验证不足、TTL 清理失败。后续再补审批/动作存储故障、执行中断、GitOps 漂移等。

每份手册包含症状、影响、检查、操作边界、缓解、恢复验证和清理，不只罗列命令。

## 15. 首批任务与完成定义

优先把上游锁定与 G0 实验、监控/告警、Gateway 契约、真实证据适配、注入/清理、恢复验证和展示材料拆成独立可 review 的工作项。接口先由双方签收；功能与集成分成小 PR。

- [ ] 满足当前阶段的共同 Gate，实际环境与报告中的架构一致。
- [ ] Agent 负责人能够用同一 fixture 和真实接口复验，不依赖你的私人脚本或文件。
- [ ] 业务症状、依赖证据和恢复结果可追溯；告警/动作成功均不替代业务验证。

- [ ] 上游归属、集成差异、资源和限制明确，未完成的能力没有被标为已交付。
- [ ] 中文文档、配置、测试、展示和双方贡献记录同步完成。
